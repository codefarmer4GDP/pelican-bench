# pelican-bench

中立的开源质量基准测试工具：对**任意 OpenAI 兼容 API 端点**（官方或中转）测量流式首字延迟、响应完整性、缓存命中迹象与计费字段清单。

- 零第三方依赖：Python 3.9+ 标准库即可运行（`urllib` / `json` / `time` / `statistics`）
- 端点中立：不内置任何厂商的端点、密钥或模型名，一切由参数提供
- 只测可观测行为：不臆测、不评级、不构成任何服务的质量认证

---

## 为什么需要它

中转站（API relay / 网关 / 聚合市场）的质量是黑盒：同一个模型名，不同上游的**首字延迟**可能差一个数量级；流式响应可能悄悄断流；非流式响应可能缺 `finish_reason` 或 `usage`；提示词缓存是否生效、缓存命中是否反映在计费字段里，往往只有跑一次才知道。pelican-bench 把这些「可观测行为」变成一张可对比、可复跑、可引用的基准报告，帮助你：

- 在多个候选端点之间做同口径对比（同参数、同轮次、同指标）；
- 在接入新上游或切换网关前后做回归验证；
- 把报告作为中性证据存档（`--json` 输出机器可读格式，方便 CI）。

## 快速开始

```bash
# 直接运行（Python 3.9+）
python3 pelican-bench.py \
    --base-url https://api.example.com/v1 \
    --api-key YOUR_API_KEY \
    --model your-model-name \
    --rounds 5 \
    --json report.json

# 或使用薄包装（自动做 python3 环境检查）
./pelican-bench.sh \
    --base-url https://api.example.com/v1 \
    --api-key YOUR_API_KEY \
    --model your-model-name

# 也可以用环境变量传密钥，避免出现在命令行历史里
export PELICAN_BENCH_API_KEY="YOUR_API_KEY"
python3 pelican-bench.py --base-url https://api.example.com/v1 --model your-model-name
```

> `--base-url` 需指向 OpenAI 兼容路径的上一级（工具会拼接 `/chat/completions`）。
> 上例中的 `api.example.com` 为占位符，请替换为你要测试的任意端点。

### 参数一览

| 参数 | 说明 | 默认 |
| --- | --- | --- |
| `--base-url` | OpenAI 兼容端点基础 URL（必填） | — |
| `--api-key` | API 密钥（必填，或环境变量 `PELICAN_BENCH_API_KEY`） | — |
| `--model` | 被测模型名（必填） | — |
| `--rounds` | 逐次请求次数 | 5 |
| `--timeout` | 单请求超时（秒） | 30 |
| `--cache-test` / `--no-cache-test` | A/B 缓存探测开关 | 开 |
| `--json FILE` | 同时输出机器可读 JSON 报告到文件 | 关 |
| `--no-stream` | 禁用流式测试 | 关 |

### 退出码（CI 友好）

| 退出码 | 含义 |
| --- | --- |
| 0 | 全部测试项通过 |
| 1 | 部分失败（如个别轮次超时、完整性检查未过） |
| 2 | 参数错误 / 连接错误（含 DNS 解析失败、拒绝连接、鉴权失败等） |

## 测试项与指标解读

### 1. 流式 TTFB 分布

对 `stream=true` 的请求逐行读取 SSE，测量**自请求发出至第一个携带非空 `content` 增量的块到达**的时间（TTFB），统计 p50 / p95 / 最小 / 最大 / 均值。

- **含义**：直接对应聊天场景里用户「等多久才看到第一个字」的体感；对 Agent / 工具调用循环，TTFB 往往比总时长更影响体验。
- **局限**：只统计首块，不评估吞吐（每秒 token 数）与流的稳定性（中途断流只体现为该轮失败）；受本机网络、时段与服务路由影响，跨机器对比需谨慎。

### 2. 非流式完整性

逐项检查每轮响应：HTTP 2xx、JSON 可解析、`choices[0].message.content` 非空、`finish_reason` 存在、`usage` 存在，输出通过率。

- **含义**：完整性差的中转往往表现为偶发 5xx、空回复、字段被截断——单次手测很难撞见，多轮统计才能暴露。
- **局限**：「完整性」只覆盖上述五项结构检查，不评判回答内容质量，也不校验字段数值的正确性。

### 3. 缓存 A/B 探测

构造一个约 2000 token 的固定长前缀（重复的中性填充文本，不含敏感内容），**连发两次完全相同的请求**，比较两次的 `usage`：记录 `prompt_tokens`、`completion_tokens`，以及若存在则记录 `prompt_tokens_details.cached_tokens`、`cache_read_input_tokens` 等缓存相关字段第二次是否 > 0。

- **含义**：如果第二次请求出现缓存读命中字段且数值 > 0，说明该端点对该模式的前缀缓存已生效——缓存是否命中直接影响长上下文场景的实际成本。
- **局限**：只是**迹象**而非证明。是否命中取决于服务端缓存策略（可能按前缀哈希、按账号、按时间窗），两次请求落在不同实例上就可能 miss；不同端点的字段命名也不统一。结论只有三种：**检测到缓存命中迹象 / 未检测到 / 字段缺失无法判定**——字段缺失时工具不会臆测。

### 4. usage 字段清单

列出响应中实际出现的 `usage` 相关键（含缓存相关），帮助核对计费口径。

- **含义**：同样标称「1K token」，有缓存字段的端点与没有的端点，实际账单可能差别很大；先看清字段，再谈单价。
- **局限**：清单只反映**本次响应**中出现的键，未出现不代表端点不支持（可能与模型、网关或计费策略配置有关）。

## 与 test-pelican.sh 的关系

pelican-bench 的测量思路源自公开脚本 [test-pelican.sh](https://github.com/codefarmer4GDP/awesome-claude-code-relay)。原脚本面向单一服务的「鹈鹕测试」场景：单次请求验证中转站 Claude 模型的输出真实性与一次性的首字延迟。pelican-bench 将这一思路通用化为对**任意 OpenAI 兼容端点**的独立基准工具，并新增了：

- 多轮分布统计（TTFB 的 p50 / p95 / 均值，而非单次测量）；
- 缓存 A/B 探测与 usage 字段清单；
- 机器可读 JSON 报告与 CI 友好退出码。

除测量思路的渊源外，两者代码相互独立；pelican-bench 不内置任何厂商端点、密钥或模型名。

## FAQ

**Q：跑一次会产生费用吗？**
会。所有请求都是真实的计费请求（这正是「测真实行为」的意义），默认配置约 `rounds × 2 + 2` 次（含预检 1 次、缓存探测 2 次），且缓存探测包含约 2000 token 的输入。请使用你自己的密钥，并知悉会产生相应费用。

**Q：需要多少额度？**
默认 `--rounds 5` 时共约 12 次请求：流式 5 次（每次输出上限 128 token）、非流式 5 次（输出上限 32 token）、预检与缓存探测各含长/短输入。粗略估计总输入约 5000~6000 token、输出几百 token，绝大多数端点成本可忽略，但请以实际账单为准。

**Q：为什么选 pelican（鹈鹕）这个名字？**
只是一个中立、易记的开源项目名，与任何厂商无关。

**Q：结果能直接当成「哪家更好」的结论吗？**
不能。结果受本机网络环境、时段与目标服务路由影响，只代表「当时、那台机器、那些轮次」的可观测行为。建议固定参数、多时段复跑、自建对比基线。

**Q：支持非 `/v1` 路径的端点吗？**
支持。`--base-url` 传到兼容层即可（如 `https://host/openai/v1`），工具只负责拼接 `/chat/completions`。

**Q：会把我的密钥或提示词上传到哪里吗？**
不会。工具零第三方依赖、无任何遥测，请求只发往你指定的 `--base-url`。缓存探测使用的是本地生成的重复填充文本，不含敏感内容。
